## 1 — Context

### What exists today

The `phoenix/verification/drift_detector.py` shipped in Phase 6b with a three-checker architecture per Decision 17:

1. **Tier-1 Analytical Checker** — runs 5 physics benchmarks (HO-1, ISW-1, H1S-1, RABI-1, SCG-1) against vendored solvers, asserts analytical tolerance.
2. **ML Statistical Checker** — wraps `ml/drift_ensemble.py::predict_scale_separated()`; **accepts an optional feature provider callback; with no provider, the checker skips.**
3. **Cross-Version Checker** — compares current Tier-1 pass/fail against the previous release's recorded results at `~/.phoenix/runtime/calibration_history/<phoenix_version>.json`.

Aggregation rule (locked):
- 0 detectors fire → `state="healthy"`
- 1 detector → `state="warning"` + `drift_warning` flag
- 2+ detectors → `state="high_confidence_warning"` → verification gate auto-promotes one rung

The orchestrator + snapshot persistence + callback registration are all production-ready.

### Why Phase 13.5 exists

The ROADMAP doc framed this as: "phoenix/verification/drift_detector.py ships with placeholder stubs. Module-level comment marks 'Phase 5 expansion' but it's now Phase 13. With Step 4 cognition axes + Step 8's prompt_disposition columns, the drift detector has real signal shapes to consume."

That framing **overstated** the gap — the checkers themselves are real. The actual gap is:

- **The ML Statistical Checker has no feature provider wired up in production.** It ships with the seam (the `feature_provider` callback parameter) but the daemon doesn't construct or register one. Today the ML checker silently skips on every cycle.
- **Cognition substrate signals (Phase 13) are not consumed by the drift detector.** The detector sees only physics-side signals (Tier-1 benchmarks). Cognition wobble axes, classifier verdicts, prompt-disposition mix, replay divergence rates — all available in the ledger, none feeding drift detection.
- **No baseline storage for cognition feature distributions.** The cross-version checker has a per-release `calibration_history` JSON; nothing equivalent for cognition signals.

## 2 — Goal

Wire the ML Statistical Checker's feature-provider seam to consume cognition substrate signals from the Omega Ledger, with a rolling-window baseline, so that drift in cognition-side behavior (classifier confidence shift, provider error rate, cognition disagreement growth) raises the existing drift detector's state via the existing aggregation rule.

**Crucially:** this design extends the existing three-checker architecture without changing Decision 17's aggregation rule. The cognition signals roll into the existing ML Statistical Checker; no new fourth checker.

## 3 — Out of scope (deferred to follow-ups)

- **Separate cognition drift detector orchestrator.** Would split physics and cognition drift into parallel orchestrators with double the cadence. Architecturally tidy but operationally heavier; deferred unless real evidence emerges that physics + cognition drift need different cadences.
- **Per-provider drift attribution** ("provider X is drifting, but Y and Z are stable"). Useful for ops; deferred — requires the cognition feature provider to surface per-provider features AND the ML statistical checker to support per-dimension drift attribution. Phase 13.5-followup.
- **Drift-triggered cognition rerouting** (the router quarantines a drifting provider automatically). Deferred to v1.2.x; this design surfaces signal, the router consumes it later.
- **Replacing the Tier-1 analytical checker with a more elaborate physics benchmark suite.** Outside Phase 13.5 scope.
- **Replacing `ml/drift_ensemble.py` with a different ML model.** The vendored model stays; we just feed it new features.
- **General drift-detector tech debt cleanup** (the ROADMAP also flagged things like "Phase 5 expansion" stale comments). Bundled-in as a small cleanup commit at the end, but not the focus.

## 4 — API surface

### 4.1 New module `phoenix/verification/cognition_drift_features.py`

The feature provider. Reads recent ledger entries via the existing `StateBackend.list_ledger_entries()` interface, computes a feature vector, returns it for the ML checker.

```python
@dataclass(frozen=True)
class CognitionDriftFeatures:
    """Feature vector for cognition drift detection.

    Each feature is computed over a rolling window (default 24h)
    of recent ENCRYPTED_OPT_IN, VERBATIM, and HASH_ONLY cognition
    ledger entries.
    """

    # Distribution shape
    classifier_verdict_bit_exact_rate: float    # 0.0 - 1.0
    classifier_verdict_semantic_match_rate: float
    classifier_verdict_divergence_rate: float
    classifier_verdict_unclassified_rate: float
    classifier_confidence_mean: float           # 0.0 - 1.0
    classifier_confidence_p10: float            # 10th percentile confidence

    # Cognition wobble signal
    cognition_disagreement_mean: float          # Mean across recent axes
    cognition_disagreement_p90: float           # Tail signal

    # Provider behavior
    provider_error_rate_overall: float
    provider_refusal_rate_overall: float
    cognition_latency_ms_p95: float

    # Disposition mix
    disposition_hash_only_rate: float
    disposition_verbatim_rate: float
    disposition_encrypted_opt_in_rate: float

    # Sample size (sentinel — if too small, ML checker should treat
    # the cycle as untrustworthy rather than drift)
    sample_size: int

    def as_vector(self) -> np.ndarray:
        """Return the 14-dimensional feature vector for the ML checker."""


class CognitionFeatureProvider:
    """Build CognitionDriftFeatures from recent ledger data."""

    def __init__(
        self,
        *,
        state_backend: StateBackend,
        window_seconds: float = 86400.0,  # 24h default
        min_sample_size: int = 50,
    ) -> None: ...

    def __call__(self) -> np.ndarray | None:
        """Read recent ledger, compute features, return vector.

        Returns None if sample size below min_sample_size
        (insufficient data for trustworthy drift detection).
        """
```

### 4.2 New module `phoenix/verification/cognition_drift_baseline.py`

Rolling baseline storage. Pattern adapts the cross-version checker's `calibration_history/<phoenix_version>.json` but for cognition feature distributions.

```python
class CognitionDriftBaseline:
    """Per-phoenix-version cognition feature baseline.

    Each baseline is a recording of the cognition feature
    distribution under "known-healthy" operation, captured at a
    deliberate moment by ops (admin command) OR auto-captured
    every N cycles when drift state has been "healthy" for the
    full N.
    """

    def __init__(self, baseline_path: Path | None = None) -> None: ...

    def write_current(self, features: CognitionDriftFeatures) -> None:
        """Record this snapshot as the current baseline for the
        running Phoenix version."""

    def read_baseline_for_version(
        self, phoenix_version: str
    ) -> CognitionDriftFeatures | None:
        """Read the baseline for the given version (or None if
        no baseline recorded)."""

    def compute_distance(
        self,
        current: CognitionDriftFeatures,
        baseline: CognitionDriftFeatures,
    ) -> float:
        """Normalized distance between the two feature vectors.

        Default: weighted L2 distance with per-feature scales
        reflecting "meaningful drift" magnitudes.
        """
```

### 4.3 Wiring change in `phoenix/verification/drift_detector.py`

The existing `MLStatisticalChecker.__init__(feature_provider=None)` already accepts the seam. The daemon-startup change is just:

```python
# Wherever DriftDetector is constructed at daemon startup:
from phoenix.verification.cognition_drift_features import CognitionFeatureProvider

cognition_provider = CognitionFeatureProvider(state_backend=state_backend)
ml_checker = MLStatisticalChecker(feature_provider=cognition_provider)
# Pass ml_checker into DriftDetector as the second checker.
```

Plus a small adjustment to `MLStatisticalChecker.run()` to consume the baseline:

```python
def run(self) -> CheckerResult:
    if self._feature_provider is None:
        return CheckerResult(fired=False, reason="ml_checker_no_provider")

    features_vec = self._feature_provider()
    if features_vec is None:
        return CheckerResult(fired=False, reason="ml_checker_insufficient_data")

    baseline = self._baseline.read_baseline_for_version(self._phoenix_version)
    if baseline is None:
        return CheckerResult(fired=False, reason="ml_checker_no_baseline")

    distance = self._baseline.compute_distance(features_vec, baseline.as_vector())

    # Existing predict_scale_separated path stays; just feed it our distance signal
    # as an additional feature OR run it independently and OR the results.
    ml_drift_signal = self._ml_predict(features_vec)

    fired = (distance > self._distance_threshold) or ml_drift_signal
    reason = f"cognition_distance={distance:.3f} ml_signal={ml_drift_signal}"
    return CheckerResult(fired=fired, reason=reason)
```

### 4.4 New admin endpoints

**`POST /v1/admin/drift/cognition-baseline/capture`** — capture the current cognition features as the baseline for this Phoenix version. Idempotent (overwrites). Returns the captured features summary. Admin-only; gated on existing `can_use_admin_endpoints` (or a more specific `can_capture_drift_baseline` flag if we want finer control — see [OPEN] below).

**`GET /v1/admin/drift/cognition-baseline`** — read the current baseline. Returns the recorded features + capture timestamp. Useful for ops auditing "what is current baseline?"

### 4.5 Auto-capture rule

When `DriftSnapshot.state` is `"healthy"` for the full `N` cycles (configurable; default 5, ~30h of healthy cycles), the daemon auto-captures the current cognition features as the running baseline.

Rationale: requires explicit human-zero (initial capture via admin endpoint), then self-sustains as ops sees drift state stay healthy after Phoenix updates / classifier retrains / provider model updates.

## 5 — Decision flow

### 5.1 Cognition feature collection (every drift cycle)

```
DriftDetector.run_cycle() invokes ml_checker.run()
  ↓
MLStatisticalChecker.run() invokes feature_provider() = CognitionFeatureProvider()
  ↓
CognitionFeatureProvider:
  1. Query state_backend for ledger entries with timestamp >= now - window_seconds
  2. Filter to entry_kind = "cognition"
  3. Compute 14 features (verdict rates, confidence stats, disagreement, provider errors, latency, disposition mix)
  4. If sample_size < min_sample_size: return None
  5. Else: return features.as_vector()
  ↓
MLStatisticalChecker:
  1. If features is None: CheckerResult(fired=False, reason="insufficient_data")
  2. Read baseline for current Phoenix version
  3. If no baseline: CheckerResult(fired=False, reason="no_baseline")
  4. Compute distance(current, baseline)
  5. Compute ML drift signal via predict_scale_separated
  6. fired = (distance > threshold) OR ml_signal
  7. Return CheckerResult(fired, reason)
```

### 5.2 Baseline lifecycle

```
First daemon start, no baseline exists:
  → ml_checker fires "no_baseline" → not counted toward aggregation
  → Ops captures baseline via admin endpoint after a known-healthy window

Steady-state with baseline:
  → Each cycle compares current features to baseline
  → If healthy for N consecutive cycles, auto-capture refreshes baseline
  → Drift state changes do NOT trigger auto-capture (we want a STABLE baseline)

After Phoenix version bump:
  → Baseline file's version != running version → no_baseline state
  → Ops must explicitly recapture for the new version
  (Or: auto-promote previous version's baseline if features compatible; defer to follow-up)
```

### 5.3 Aggregation unchanged

The three-checker aggregation rule from Decision 17 is preserved:
- 0 fire → healthy
- 1 fire → warning
- 2+ fire → high_confidence_warning + auto-promote

The cognition extension makes the ML checker more **likely to fire** (it now has signal to consume); aggregation logic is untouched.

## 6 — Open tensions

- **[OPEN: baseline-bootstrap]** — On first install, NO baseline exists. The ml checker won't fire on cognition drift until ops captures one. Two options:
  - (a) Require explicit ops admin-endpoint call to capture initial baseline. Documented in setup ceremony.
  - (b) Auto-capture after N consecutive cycles, even if first-ever (treating the first stable window as "zero baseline").
  Recommendation: (a) — explicit human-zero matches the Phase 13.x.6 encryption ceremony pattern (ops actively wires the daemon). (b) makes drift detection "magic" and harder to reason about.

- **[OPEN: baseline-per-version]** — When the Phoenix version bumps, should the baseline:
  - (a) Be invalidated (require fresh capture)
  - (b) Be auto-promoted (assume backward compatibility unless features changed shape)
  Recommendation: (a) — version bumps may change classifier model OR feature definitions; requiring fresh baseline forces ops to actively review.

- **[OPEN: cognition-distance-threshold]** — The `distance_threshold` is a hyperparameter. Three approaches:
  - (a) Fixed default (e.g., 0.5) with env-var override (`$PHOENIX_DRIFT_COGNITION_THRESHOLD`).
  - (b) Per-baseline learned threshold (capture baseline + record its observed std; threshold = baseline_mean + 3*baseline_std).
  - (c) Adaptive (start with default, adjust after N false-positive cycles).
  Recommendation: (a) for v1.1.x; (b) is the right long-term answer but adds complexity.

- **[OPEN: feature-set-stability]** — The 14-feature list will likely grow over time (e.g., add per-provider features in a future slot). When features are added, baseline files become incompatible. Mitigation:
  - Each baseline file records its `feature_schema_version: int`; on load, mismatch → `no_baseline`.
  - Schema bumps are documented in CHANGELOG so ops knows when to recapture.
  Recommendation: implement schema versioning from day 1.

- **[OPEN: privacy]** — The cognition feature provider reads ledger entries; ENCRYPTED_OPT_IN entries have encrypted prompts but their VERDICT + CLASSIFIER metadata is in cleartext. Reading aggregates only (rates, means, percentiles) doesn't leak per-prompt content. No new privacy concern; CONFIRM in implementation that the feature provider does NOT read `prompt_verbatim` or `prompt_encrypted`.

## 9 — Risks and mitigations

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Feature provider's ledger query is slow on large databases | Medium | Add timestamp-indexed query; cap window read at last 10k entries. |
| ML checker false-positives flood ops with warnings | Medium | Distance threshold tuned conservatively in initial deploy; auto-capture pattern stabilizes baseline over N cycles. |
| Feature schema change breaks existing baselines | High (over time) | Schema versioning on baseline file; mismatch → no_baseline → ops recaptures. |
| Privacy leak via feature extraction | Low | Aggregate-only computation; design call confirms no prompt_verbatim / prompt_encrypted read. |
| Auto-capture refreshes baseline during slow-creeping drift (masks the issue) | Medium | Auto-capture only when state has been healthy for N consecutive cycles; if drift is fired, no auto-capture (stable baseline preserved). |
| Cognition feature provider depends on cognition ledger entries existing | Low | Feature provider returns None if sample_size < min; ml checker reports "insufficient_data" instead of treating empty data as healthy. |

## 10 — Scope summary

This is **medium scope**, smaller than 13.x.4 or 13.x.8 because:
- The drift detector orchestrator + 3 checkers + snapshot persistence + callback registration already exist
- Only the ML Statistical Checker needs wiring + the new feature provider + baseline storage
- Tier-1 and Cross-Version checkers untouched

Realistic implementation budget: ~2-3 hours including subagent-driven test/review cycles. Smaller than 13.x.8.

## 11 — Naming clarification

This design is for **Phase 13.5** in the ROADMAP doc's framing (between Phase 13 and a future Phase 14 perception harness).
